# P4B v1：单制度混合审核扩展

P4B 默认关闭，只能在已配置 PostgreSQL 权威制度、P4A 与企业模式的实例中启用。新增契约版本为 `p4b.1`，路由前缀为 `/api/v1.5/p4b/v1`；不修改冻结 v1.0–v1.4 DTO/OpenAPI。旧 v1.5 详情仅增可选 `compliance_analysis`，历史在途审核保持原路径。

## 原文与权限

唯一支持的源文件是项目夹具 `tests/fixtures/policies/p4a-222.docx`，SHA-256 为 `65043838143a8d043130881b8fda35fd2573ed7fcd8716f1a33fc72f32bf1a98`。正文有效期保持 `[2026-11-01, 2027-01-01)`。本轮日期模拟仅用于隔离测试，不能用于正常实例提前报销。

先使用既有 P4A 上传、原文核对、16 格矩阵确认、冲突处理及 PostgreSQL 显式发布。ADMIN 再逐项核对本文件正文、完整日补助与一般客户招待的提取摘要，并调用 P4B 范围确认；这个独立、不可变的确认不修改旧类别发布记录，也不将旧交通规则转换为新制度。没有该确认时，新 P4B 审核不能通过。上传、索引、员工说明均不产生权威。

所有路由复用企业会话、角色及公司/申请所有权检查；员工不能自行核实事实，核实人不能核实本人的申请。鉴权、财务最终决定、Hard Gate、原 P4A 权威复核及 ERP 幂等继续使用原实现。

| 路由 | 身份 | 行为 |
|---|---|---|
| GET `/runtime` | 已登录 | 明示当前语义 provider/model 与本地文本检索能力 |
| GET `/policies/{pid}` | ADMIN | 读取已发布且源 SHA 一致的正文、表格与规则提取摘要 |
| POST `/policies/{pid}/confirm-scope` | ADMIN | 明确确认摘要 digest、理由与幂等键，写不可变范围记录 |
| POST `/claims` | EMPLOYEE | 提交 ALLOWANCE 或 ENTERTAINMENT，服务器生成真实 UUID 单号、身份、持久化声明并启动既有图 |
| GET `/claims/{cid}` | 申请本人或同公司 FINANCE/ADMIN | 读取当前独立报告、事实核实版本和来源留痕 |
| GET `/claims/{cid}/evidence/{chunkid}` | 同上 | 从原始 Word 字节重新定位并核对当前报告引用 |
| POST `/claims/{cid}/verify` | FINANCE/ADMIN | 带 expected_revision、确认、实际来源、核实依据及幂等键追加严格类型的事实核实记录 |
| POST `/claims/{cid}/reaudit` | FINANCE | 对尚无最终决定/ERP 的待财务或退回申请启动新审核，保留旧图、旧报告与版本 |

住宿继续通过既有 `/p4a/v1/claims` 提交。新补助和招待申报可以绑定既有发票草稿/附件/OCR/员工确认，不能凭空生成票据。供餐次数只是员工候选声明；没有财务独立核实，金额规则保持 UNKNOWN。一般客户招待以已核实人数同时计算人均和单次限额；其他招待类别、部分出差日和多城市分段不属于本轮自动计算范围。

P4B 的补助/招待原申报保持不可变。退回后，财务可以核实补充凭据并重审；修改原申报金额或事项需另建单。旧通用 resubmit 路由拒绝写入 P4B 申请，防止绕过其声明、事实核实和版本绑定。P4A 住宿仍保留原独立重提入口；员工改变申报后，旧核实记录不会继续作为新事实使用。

## 计算、语义与决定

酒店限额仍调用未修改的 P4A `rules/hotel_matrix.py`。补助与一般客户招待标准从确切正文表格提取，经 ADMIN 明确核对后使用；只用已核实输入做 Decimal 计算。旧差旅补助与 P4B 复用 `rules/allowance.py` 的算术，旧交通/补助发布路径保留。

正文按章、条和完整表头/行关系定位，保留 document ID/SHA、版本 ID、章节、条款 ID、chunk ID、实际文字、OOXML body/table/row 位置及生效区间。全部附录排除。PostgreSQL 按公司、城市、费用日期、发布/退休时间及冲突过滤后，才进行本地文本相关性排序；没有伪造页码，也没有把 deterministic vector 称为真实语义检索。证据、审批、异常及版本治理条款优先保留，实际模型请求遵守已有 32 KB 输入界限；无法保留必要上下文时安全失败。

`ComplianceAnalysis` 独立保存原规则结果、可信职级/城市、事实版本、完整 `semantic_assessment`、结构化 findings、真正送给模型的 supporting evidence、缺失/冲突/例外、汇总风险、合规状态、处理建议、provider/model/status 与安全调用元数据。`semantic_assessment` 是模型的原始结构化建议，外层 `suggested_risk` 和 `recommended_action` 是确定性汇总后的风险与建议，不是付款授权。

每项发现须有真实引用、实际事实键路径、结论、说明及不确定性。希望输出 CHECK_PASSED 的模型必须分别覆盖业务用途、制度适用、例外理由、事实/制度冲突、证据充分性、重复/拆单/类别、授权及未决问题八项；仅复述 `rule_results` 无法通过输出门禁。员工声明不能自行成为已核实事实，OCR/票据确认信息也明确标记为非权威候选证据。

硬门禁失败、硬性超额、UNKNOWN、缺证、制度冲突、模型或检索故障均阻止批准。例外进入补证/人工处理，本轮没有开放例外付款通道。即便检查通过，也必须完成原财务流程；人工批准时再次核对制度、原件完整性、原规则、事实版本和可信主数据。更正事实须启动新审核，不能覆写原报告。图恢复使用已有持久化检查点；同一审核报告已固定时，不重复发出语义请求。

## 默认与边界

`P4B_ENABLED=false`、`P4B_LIVE_LLM=false`；前端 `VITE_P4B_ENABLED` 默认关闭。Mock 明确输出 UNSUPPORTED，不能证明语义能力，也不能据此完成财务批准。开启真实语义须明确 opt-in DeepSeek，独立输出预算默认为 4096 tokens；传输、超时、重试和故障处理复用现有 provider。没有修改 .env、运行实例、网络、CORS 或业务数据库。

真实 DeepSeek、远程 BGE-M3、Chrome 完整验收与生产/真实 ERP 均需分别报告，不能从离线工程 PASS 推断通过。P4B 当前使用本地文本检索；未将远程语义检索接入此路径或完成相关验收。并发与部署仍沿用原 Demo 单进程边界，未声称生产或多进程财务验收。
