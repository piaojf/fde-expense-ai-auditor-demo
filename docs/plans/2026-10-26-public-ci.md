# Public CI and Documentation Implementation Plan

**Goal:** Make public pull requests independently verifiable, repair the optional browser entry point, and improve the README without adding video/screenshots or touching the recording runtime.

**Architecture:** A read-only reusable CI workflow runs Python public tests, frontend checks and a synthetic browser flow, then reports one required aggregate check. A manually dispatched release workflow accepts an existing version tag at main, reruns CI and publishes checksummed source/frontend archives. Only the final release job receives write permission.

**Tech Stack:** GitHub Actions, Python 3.12, Node.js 24, Playwright Core, preinstalled Chrome, Tesseract, GitHub branch protection and security settings.

## 1. Isolate

- Work from the current public main in a new worktree/branch.
- Preserve both private source worktrees, the active recording services, databases, policy sources and model budget.
- Resolve third-party Actions to official commit SHAs and add no paid-provider credentials.

## 2. Browser and dependency entry points

- Add the pinned Playwright Core dependency, frontend test scripts and Node engine guidance.
- Add `scripts/public_e2e.py` to validate explicit loopback consent, refuse occupied ports, build the basic Mock frontend, start only owned child processes, run the existing real browser flow and always clean up its own processes.
- Exercise occupied-port refusal and argument validation. Run browser acceptance on the isolated GitHub runner, using installed Chrome without downloading a browser bundle.

## 3. Automation

- Add `.github/workflows/ci.yml`: public Python profile/Ruff/pip check, frontend typecheck/tests/build, browser Mock flow, artifacts and `Required CI`.
- Add `.github/workflows/release.yml`: manual existing-tag validation, reusable CI, checksummed source/basic frontend release archives. No website or production deployment.
- Add a concise PR template and weekly Dependabot update requests.

## 4. Documentation

- Rewrite README around business purpose, capability/reproduction table, installation, expected result, testing and CI/release status.
- Leave video and page screenshots for the maintainer's next step; add no fake image/video links.
- Repair the Shadow documentation link, document CI/release commands and expand Docker context exclusions for runtime artifacts.
- Preserve all public/private source and licensing boundaries.

## 5. Validate and publish

- Validate workflow syntax, public backend tests, frontend checks and lockfile resolution locally where applicable.
- Push a public PR, inspect real GitHub Actions results and repair concrete failures.
- After the required check succeeds, require PRs and `Required CI` on main, disable force push/deletion, and enable available dependency/secret protection.
- Merge the PR through the checks, verify main's CI and report exact workflow/security state. No release tag or production deployment is created during setup.
